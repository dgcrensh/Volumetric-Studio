# L4 — Procedures that emit child volumes (plan)

Nov 20, 2026 · follows L3 · decision record: `docs/decisions/0022-generated-child-volumes.md`

**Status: built.** As below, with these differences found while building
it (decision 0022 has the details): templates carry an `origin` and
generated copies a `contents_offset`, because sketches are placed in
model coordinates and a parametric template would otherwise fill every
copy in the same place; a wrong output node for the volume's kind is its
own code, `proc.graph.output_kind` (`proc.graph.output` alone counts as
"unfinished" in the editor), and a template the composite lacks is
`proc.reference.template`; generated children's names needn't be
distinct; read-only generated rows are refused with a status message
rather than a code; and the composite's menu also has Stop generating
children. A shared scene, `libs/vs_model/tests/rack.*`, is the rack used
by every suite.

## Goal

Let a composite's children come from a procedure, so nested volumes can be
authored by rule instead of one by one. The spec's example is "many
copies of a parametric bracket template, each sized by the procedure": a
rack split into a grid of cells, each cell filled from the same template;
bosses placed at a pattern of frames; a stack whose layer count is a
parameter. The spec's rule is the acceptance: "Children receive
boundaries and connection surfaces generated by the procedure, belong
entirely to the parent, cannot be referred to from outside, and must pass
the overlap and containment checks."

L3 built everything a generated layout needs to land in: composites, their
own layout, levels, delegations, sibling overlap and nesting checks, the
weld through delegated surfaces, and the engine's composite status. L4 adds
the generating half and routes its result through exactly that.

## The model: a composite may have a generator and templates

`CompositeContents` gains two optional members (written to JSON only when
set, so every L3 document, content hash and cache key is unchanged):

- **generator**: a procedural graph (vs_proc JSON, opaque here as in
  `ProceduralContents`) whose output is a set of children instead of a
  field;
- **templates**: what generated children are filled from. A
  `ChildTemplate` has an id, a name, contents (static, parametric or
  procedural; not composite, so nesting stays one generated level per
  composite), parameters and published outputs. A parametric template's
  tree refers to its boundary by the template's id (faces `-x`..`+z`, as
  a box volume's tree does), so the easiest way to make one is from an
  authored child: **Make template** keeps the child's id as the
  template's, and every reference in its tree stays valid.

A composite with a generator may still have authored children; generated
ones are their siblings and every check treats them alike.

## What a procedure emits: a generated layout

`model::GeneratedLayout` (new, `generated.hpp`) is plain data:

- **children**: each with a key (stable across regenerations: the
  emitting node's id and an index), a name, a template name (empty: a
  placeholder), an axis-aligned box in model coordinates, parameter values
  by name, and a seed;
- **surfaces** between two of those children: a key, a name, bonded or
  clearance (with its gap), and a rectangle on an axis-aligned plane;
- **delegations**: which generated child meets each surface that joins the
  composite from outside.

`model::expand(document, composite, layout)` writes it into a copy of the
document as if authored: datum points and planes appended to the
composite's layout (ids derived from the composite and the key), child
volumes with box boundaries between those points (`Volume::generated`
set, id `derive(composite, key)`), each a copy of its template with every
id in it derived from the child's id (the template's own id becoming the
child's), parameters set from the procedure's values, datum-patch
connection surfaces, and the delegations. Expansion is pure and
deterministic: the same layout gives the same document, byte for byte.
Codes: `model.generated.template` (no such template),
`model.generated.parameter` (the template has no such parameter),
`model.generated.surface` (a surface's children or rectangle are wrong).

Generated volumes never reach a saved project: they exist only in the
evaluated document (`Evaluation::document`). Nothing authored can name
them, so "cannot be referred to from outside" holds by construction, and
the evaluated document is still run through `check()`.

## Nodes (vs_proc)

A new port type, **Children** (appended, so existing types and value
hashes are unchanged), holds a generated layout. Nodes:

- `children.grid`: splits the composite's boundary box into `count`
  (nx, ny, nz) cells, each from `template`; neighbouring cells are joined
  by a `join` surface (bonded or clearance, with `gap`), inset from the
  face edges by `margin` so no two seams share an edge.
- `children.at_frames`: a box of `size` centred at each frame (axis
  aligned: the frame's rotation is ignored), from `template`, unjoined.
- Both take an optional `values` list and a `parameter` name: child k's
  parameter takes `values[k]`, which is how a procedure sizes each copy.
- `children.merge` (two sets into one), `children.delegate` (passes a
  surface joining the composite to the child whose box face lies on the
  patch and contains its centre; infeasible when none does).
- `output.children`: the generator's output. A graph has exactly one
  output node, `output` or `output.children`; a composite's generator
  needs the second and a procedural volume the first (`proc.graph.output`).

## Engine

`Engine::set_layout_generator()` plugs the generator in (vs_proc's
`install()` does it). `evaluate()`, after `check()`, when any composite
has a generator:

1. builds the layout once and, for each generating composite whose
   boundary built, runs its generator on the calling thread (inputs as for
   a procedural volume: boundary, joining surfaces, parameters, seed),
   cached in memory by the composite's own key;
2. expands each result into the evaluated document and checks it; a
   generator that fails, or an expansion that `check()` refuses, leaves the
   composite with no generated children and Failed, with the diagnostics;
3. carries on exactly as L3 on the expanded document: the layout checks
   (overlap between siblings, `validate.nesting.outside`, connection
   rules), then the children generate in waves, containment per leaf, the
   composite takes the worst of its children's statuses and sums their
   measures, the weld follows the delegations.

A generated layout that fails a layout check (overlap, nesting, contact,
connection rules) fails its composite: "must pass the same checks" is a
status, not only a list of warnings. Documents without a generator take
exactly today's path (no extra layout build).

**Links.** The generator runs before links carry values, so a link into a
generating composite's inputs would be ignored by it. L4 refuses that at
authoring (`model.composite.generated_link`). Driving a generator from a
published output is left for later.

## App

- Generated children appear in the volume tree under their composite,
  marked generated, read-only: no edit in context, swap, delete or
  Make template (`app.generated.read_only`).
- The Graph dock edits a composite's generator as it does a procedural
  volume's graph (the palette offers the children nodes there, and their
  template property lists the composite's templates).
- **Make template** on an authored child of a composite turns it into a
  template of that composite (undo restores identical hashes).

## Tests (acceptance)

1. JSON round-trips a composite with a generator and templates; every L3
   document, sample, content hash and golden value is unchanged.
2. Expansion: ids derived and stable, template references remapped,
   parameters applied, the same layout twice gives the same document;
   each `model.generated.*` refusal.
3. Nodes: grid cells tile the boundary exactly with surfaces between
   neighbours; at_frames places boxes; values size each child; delegate
   finds the child on the patch; the output rules.
4. Engine: a 3 × 2 grid of parametric cells evaluates, every cell
   current, the composite's volume the sum of its cells', determinism on
   1 and 4 threads; changing the count regenerates; changing one cell's
   value regenerates only that cell and its composite.
5. The same checks: an at_frames layout with overlapping children fails
   the composite with `validate.overlap`; one reaching outside it with
   `validate.nesting.outside`; contents not contained with
   `validate.containment`.
6. Weld: a generated grid joined to a root volume through a surface the
   generator delegates welds into one closed manifold mesh of the right
   volume, with parametric and procedural templates.
7. App: generated rows nest and refuse editing; Make template then a grid
   generator rebuilds the cells; undo restores hashes.

## Out of scope

Generated composites (a template can't be a composite, so one generated
level per composite); boundaries other than axis-aligned boxes; links
driving a generator; editing a generated child (change the procedure or
the template); a seam split across several children.
